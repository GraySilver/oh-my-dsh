# Agent Note: 移动端工作台使用覆盖层而非压缩列

Status: implemented

[English](2026-08-15-mobile-workbench-shell.md) | 中文

## 问题

工作台外壳在所有视口宽度下都使用桌面端三列网格。它的窄屏状态会把侧边栏收起为 56px 轨道，但打开后又会在同一网格中恢复 280px 列。在 390px 视口中，会话区因此只剩约 110px。详情列则遵循桌面端让步求解器并收缩为零，而非展示其内容。两种结果都保留了桌面端几何，却让用户要操作的表面无法使用。

会话与设置内部也存在缩小版的同类错配。新会话 hero 把工作区、任务启动器与 agent 预设控件放在同一行；composer 把两组工具保留在同一行；设置对话框则保留 188px 纵向导航轨道。即使中间列本身已经有可用宽度，这些控件仍会争抢空间并相互重叠。

## 决策

当框架宽度小于或等于 640px 时，`AppFrame` 继续挂载现有的侧边栏、会话、详情与覆盖层 slot 内容，但不再让两个侧列参与网格尺寸计算。收起的侧边栏显示为全宽 56px 顶部工具栏。展开后，同一侧边栏子树显示为带遮罩的抽屉，宽度上限为 320px，并留出 48px 页面窄条。选择另一个会话、点击遮罩或按 Escape 都会关闭抽屉。由框架拥有的详情表面会覆盖整个框架，并比抽屉优先消费 Escape；无障碍模态框仍拥有自己的 Escape 生命周期。

同一断点只改变现有组件内的呈现。hero 让工作区选择与产品控件分居两行，composer 让左右工具组分居两行，设置页则把现有标题、操作、导航与 section 内容呈现为标题行、可水平滚动的分类行与内容行。提供方编辑器与 agent 预设卡片可以换行或收为单列。在 640px 以上，原有网格轨道、侧边栏轨道、详情缩放、hero 行、composer 行与设置导航轨道仍是生效的级联。

## 曾考虑的替代方案

**继续压缩桌面端列。** 这能保留一套几何算法，但 280px 导航列无法在手机上与可用的会话区并存，详情也仍然没有可用宽度。之所以否决，是因为根本问题在于同时呈现，而不是缺了一个最小宽度常量。

**构建独立的移动端组件树。** 专用的移动端侧边栏、composer 与设置实现可以独立设计样式。之所以否决，是因为它们会重复会话选择、对话框局部状态、slot 注册、焦点管理与配置写入。现有内容已经拥有正确行为；只需改变它们的窄屏几何。

**只让明显重叠的控件换行。** 局部换行可以改善 hero 与 composer，却会让打开的侧边栏和详情行为保持损坏。之所以否决，是因为它只修补了框架下层的症状，没有闭合移动端导航与检视路径。

## 后果

移动端外壳每次只有一个主表面：会话、导航抽屉、全框架详情或模态框。后端 API、配置形状、CLI、slot 键与会话身份模型都不变。`SidebarOwnerProps` 增加由框架派生的 `mobile` 呈现事实，并报告抽屉宽度，使现有侧边栏能渲染正确姿态。

640px 边界现在同时存在于框架的 TypeScript 呈现决策与组件媒体查询中。行为测试固定了移动端零宽网格轨道、抽屉关闭、会话变更时关闭、模态框的 Escape 所有权、全框架详情与移动端新会话行为。由于 jsdom 无法证明渲染矩形或发现视觉重叠，仍需在移动端与桌面端宽度下做浏览器验收。
